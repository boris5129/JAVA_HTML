1. 서블릿 실행 시점과 생명주기 (init과 doGet)URL 매핑의 의미: 컨트롤러(서블릿) 클래스에 URL을 정의하는 것은 "이 주소로 요청이 들어오면 처리할 수 있다"는 약속(정의)일 뿐이며, 코드를 작성했다고 해서 바로 실행되는 것은 아닙니다.   init() 실행 시점:클라이언트가 해당 URL로 최초 요청을 보냈을 때 딱 한 번 실행됩니다.   톰캣(WAS)이 서블릿 인스턴스(객체)를 메모리에 생성하고 초기화할 때 호출됩니다.   doGet() / doPost() 실행 시점:init()으로 초기화된 이후, 들어온 요청 방식(GET, POST 등)에 맞춰 실제 작업 로직을 수행하기 위해 매 요청마다 반복 호출됩니다.   2. RequestDispatcher와 포워딩(Forward) 흐름데이터 세팅: 서블릿에서 처리한 결과 데이터(예: userList)를 JSP로 넘겨주기 위해 request.setAttribute("key", value) 형태로 Request 객체에 담습니다.   포워딩 전달:RequestDispatcher를 통해 클라이언트의 현재 요청을 지정된 JSP 파일 경로로 넘깁니다(forward(request, response)).   이때 기존 서블릿이 가지고 있던 request와 response 객체 자체가 JSP로 그대로 전달됩니다.   JSP 내장 객체:JSP는 request, response, application, out 등의 내장 객체를 기본적으로 가지고 있어 별도의 매개변수 선언 없이 바로 사용할 수 있습니다.   따라서 JSP 페이지 내에서 request.getAttribute("key")로 서블릿이 담아둔 데이터를 꺼내 화면(HTML)을 구성할 수 있습니다.   최종 응답 주체:서블릿에서 바로 브라우저로 응답이 끝나는 것이 아니라, JSP가 완성한 HTML 결과물이 최종적으로 톰캣을 거쳐 클라이언트에게 전송됩니다.   3. 응답 방식의 선택 (JSP vs JSON)컨트롤러를 만들었다고 해서 반드시 JSP 화면을 만들어야 하는 것은 아닙니다.   화면 응답: HTML 화면이 필요한 경우 JSP로 포워딩하여 뷰를 렌더링합니다.   데이터 응답 (API): 데이터 자체만 필요한 경우 JSP 없이 JSON 등의 데이터 포맷으로 직접 응답합니다.   4. 계층별 개발 순서에 대한 조언 (Controller vs Service vs Repository)초보자/학습 단계:컨트롤러부터 진입하면 "어? 서비스를 호출해야 하네?", 서비스로 가면 "레포지토리가 필요하네?"처럼 필요한 도구를 역으로 찾아가는 경험을 하게 됩니다.   처음에는 컨트롤러부터 작성하며 필요한 하위 계층을 만들어 나가는 흐름이 전체 구조를 체감하기에 자연스럽고 정상적인 학습 과정입니다.   숙련 단계:데이터 흐름과 도메인 모델에 익숙해지면 어떤 DB 작업과 비즈니스 로직이 필요한지 사전에 파악되므로, 자연스럽게 Repository → Service → Controller 순서로 설계·구현하게 됩니다.
